# 第 13 课：Guard、当前用户与数据所有权

## 学习目标

- 用全局 Guard 建立默认拒绝策略。
- 理解验证 JWT 后仍需加载当前用户。
- 把资源所有权落实到数据库查询条件。

建议先只学习 Guard 与 `@Public()`，确认 401/公开路由后，再学习 ownerId 和嵌套任务作用域。

## 本课从"能登录"走到"只能看自己的数据"

上一课解决了"你是谁"，这一课解决"你能干什么"。这是两件完全不同的事：认证是确认身份，授权是确认权限——登录成功了，不代表你能看别人的数据。

这一课加一个全局的 Guard，默认拦住所有路由，只有明确标了 `@Public()` 的注册和登录能匿名访问。这种"默认全部拒绝，白名单里的才放行"的思路，比每加一个新路由都要记得手动加保护要安全得多——你总有一天会忘记加。

## 请求链路

```text
Authorization: Bearer JWT
       -> JwtAuthGuard 验签
       -> 用 sub 查询数据库中的最新用户
       -> request.user
       -> @CurrentUser() 注入 Controller
       -> Service 查询 { id, ownerId }
```

Guard 验证令牌之后，不会直接信任令牌里可能已经过时的邮箱、昵称，而是拿着令牌里的用户 ID 重新去数据库查一次最新的用户信息，顺便也确认了这个用户现在还存在。

## 所有权不是 Controller 的 if

"所有权"该怎么判断——不是查出一条数据以后在代码里写个 `if` 判断这条数据是不是你的，而是应该在查数据库的那一步，直接把"这是我的数据"作为查询条件的一部分：项目查询直接带上 `ownerId`；任务的访问，先确认它所属的项目是不是你的，再按项目 ID 和任务 ID 一起查。这样查出来的结果本身就已经是"属于你的"，不会有查出别人数据、只是忘了判断一下就返回出去的风险。找不到和越权统一返回 404，不让人从错误码的差异猜出"这条数据到底存不存在"。

## 所有权字段如何迁移

这一课没有去改第 12 课已经存在的初始 Migration，而是新写了一条 `1740000000000-add-project-owner.ts`。`ownerId` 这个字段先设成"可以为空"，是因为真实系统升级的时候，可能已经有一批老项目，一时半会填不出它们该属于谁。

真实项目里，这种改动通常分几步走：先加一个允许为空的列和索引，回填老数据，部署新代码，最后再用下一条 Migration 把它收紧成"不能为空"、加上外键约束。这门课没有老数据，所以代码创建的新项目一开始就会写 `ownerId`；留着"可以为空"这一步，是为了让你见识一次安全的分阶段演进方式，不代表业务上真的允许没有主人的项目存在。

## 运行

1. 启动：`npm run lesson -- 13`
2. 注册，复制 `accessToken`。
3. 不带 token 请求 `GET /projects`，应得 401。
4. 带 `Authorization: Bearer TOKEN` 创建和读取项目。
5. 再注册第二个账号，用它访问第一个账号的项目，应得 404。

为 Project 增加删除接口。删除前必须用 `{ id, ownerId }` 找到实体；用两个账号证明越权用户删不掉它。

## 常见错误

- 给少数路由手工加 Guard，新增路由时忘记保护。
- 验签后永久信任 JWT 内旧邮箱或昵称，不确认用户是否仍存在。
- 先按 ID 查出资源，再在 Controller 做 owner if，容易在其他调用入口漏检。
- 越权返回 403、资源不存在返回 404，从而泄露资源是否存在；本课程统一为 404。

## 完成标准

- 匿名请求默认 401。
- 注册和登录仍公开。
- `/auth/me` 返回数据库中的最新公开用户。
- 用户只能读写自己项目下的数据。
